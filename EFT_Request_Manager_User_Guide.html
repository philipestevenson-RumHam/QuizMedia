Pepper Money — Internal Tooling

EFT Request Manager
User Guide

Everything you need to know about managing Electronic Fund Transfer requests — from creating your first entry through to final completion or failure.

Version 1.0 May 2026 Pepper Money Operations

1 Overview

The EFT Request Manager is a browser-based tool built by Pepper Money to manage the end-to-end lifecycle of Electronic Fund Transfer (EFT) requests. It runs entirely in your web browser — no installation, no server, no internet connection required after the page loads.

All data is stored in a plain CSV file on your local drive or network share, which means it can be accessed by multiple team members simultaneously and is easy to back up, archive, or open in Excel when needed.

What it tracks

  • Who requested the transfer (User) and which project it belongs to
  • The originating pool account (our internal reference)
  • Customer bank details: name, sort code, and account number
  • Transfer amount in GBP (£)
  • Full audit trail: when added, edited, checked, sent, and completed
  • Who checked, sent, and completed each transfer

The five statuses

Pending
Request has been entered. Awaiting review and check by a second person.
Checked
A second person has verified all details. Ready to be sent to the bank.
Sent
Export has been sent to the payment system. Awaiting outcome confirmation.
Completed
Transfer was processed successfully. Terminal state.
Failed
Transfer failed (e.g. rejected by bank). Terminal state. Requires investigation.

2 Getting Started

Browser Requirements

⚠
The EFT Request Manager requires Google Chrome or Microsoft Edge (version 86 or later). It will not work in Firefox, Safari, or Internet Explorer. This is because it uses the File System Access API to read and write CSV files directly on your computer.

To open the application, simply double-click the EFT_Request_Manager.html file. It will open in your default browser. If your default browser is not Chrome or Edge, right-click the file and choose Open with > Google Chrome or Open with > Microsoft Edge.

Opening or Creating a File

When the application first loads you will see a welcome screen with two options:

  1. Open Existing File

    Click "Open Existing File" to open a previously saved CSV file. A file browser will appear — navigate to and select your .csv file. Your browser will ask for read/write permission to that file — click Allow or Grant Access. You only need to do this once per session.

  2. Create New File

    Click "Create New File" to start a fresh data file. A save dialog will appear — choose a location (e.g. a shared network drive) and give the file a meaningful name such as EFT_Requests_2026.csv. The file is created immediately with just the header row and is ready for entries.

💡
Shared network drive? If your team is sharing a single CSV file, save it to a shared network location that all users can access. Each user opens the same file in their own browser. The tool will automatically sync changes from other users every 15 seconds.

Stats Bar

Immediately below the header you will see a row of six summary cards:

These totals update in real time whenever a record is added, edited, or its status changes.

Toolbar & Table

The main Requests tab contains a toolbar above the data table. From left to right:

  • Search box — instantly filters records by any visible field (user, project, pool, customer name, sort code, account number, status, and more).
  • Status filter — dropdown to show only records at a particular status (All, Pending, Checked, Sent, Completed, or Failed).
  • Export button — opens the export dialog (see Section 8).
  • + Add Request — opens the form to create a new EFT request.

The table itself shows all records matching the current search and filter. Click any column header to sort by that column; click again to reverse the sort direction. A small arrow (▲ / ▼) shows which column is currently sorted.

Row colours indicate status at a glance: white = Pending, light blue = Checked, light green = Sent, pale green = Completed, pale red = Failed.

ℹ
Detail view: Double-click the status badge on any row to open a full read-only detail panel showing every field, including the complete audit trail (who checked it, who completed it, and when).

4 Adding a Request

Click the red + Add Request button in the toolbar. A modal dialog will appear. All fields marked with an asterisk (*) are mandatory — the form will not save until all are filled.

Field Reference

Field Description Example
User Required The name or identifier of the person making the request. Used for filtering and audit purposes. J.Smith
Project Required The project, case, or reference code this transfer relates to. PRJ-2026-001
Pool Required The Pepper Money pool or funding account that the transfer originates from. POOL-01
Pool Account Number Required The account number associated with the pool. Stored as text to prevent Excel from modifying it. 12345678
Customer Name Required The full name of the customer receiving the funds. Jane Doe
Customer Sort Code Required The 6-digit UK sort code of the receiving bank account. Stored as text to prevent Excel treating it as a date. 12-34-56
Customer Bank Account Required The receiving bank account number. Stored as text. 87654321
Amount (£) Required The transfer amount in GBP. Must be greater than zero. Supports up to two decimal places. 1,500.00

Once all fields are filled, click Save Request. The record is added with a status of Pending and the current date/time is recorded as the "Time Added". A yellow dot will appear on the Save button in the header, indicating there are unsaved changes.

⚠
Adding a record does not automatically save the file. You must click the Save button in the header to write changes to disk — unless the tool triggers an auto-save (which happens automatically on status changes and deletes).

5 The EFT Workflow

Every EFT request follows a strict progression through five states. Understanding this pipeline is central to using the tool correctly.

Pending
→
Checked
→
Sent
→
Completed
or
Failed

Step 1 — Pending (Requester)

A request starts as Pending as soon as it is saved. At this stage, the requester should verify their entry is correct. The record can still be edited or deleted while it is Pending.

Step 2 — Checking (Second Person)

A different person from the requester should carry out the check. This is a four-eyes control to catch errors before funds are moved. To check a request:

  1. Click the blue check button (✓) in the Actions column

    The Check modal will open. All fields are read-only — you are reviewing, not editing.

  2. Review all details carefully

    Verify the customer name, sort code, account number, amount, and pool against your source documentation.

  3. Enter your name in the "Checker's Name" field

    Your name is recorded in the audit trail along with the current timestamp.

  4. Click "Confirm Check"

    The status changes to Checked and the file is auto-saved. The edit and check buttons are now disabled to prevent further changes.

⚠
Important: Once a request is marked as Checked, it cannot be edited. If an error is found after checking, the record must be deleted and re-entered. This protects the integrity of the audit trail.

Step 3 — Marking as Sent (Operations)

Once checked records have been exported (see Section 8) and submitted to the bank or payment system, they are automatically or manually marked as Sent. The export process includes an option to mark all exported Checked records as Sent in a single step.

ℹ
The "Mark exported Checked records as Sent after export" checkbox in the Export dialog is the recommended way to transition records from Checked to Sent — it keeps the export and status update in perfect sync.

Step 4 — Completing or Failing

Once the bank has processed the payment (or rejected it), a team member should close out the request. To do this:

  1. Click the green complete button (✔) in the Actions column

    This button only appears on Sent records.

  2. Review the read-only details

    Confirm you are looking at the correct record.

  3. Select an outcome: Completed or Failed

    Use "Completed" if the funds transferred successfully. Use "Failed" if the bank rejected or returned the payment.

  4. Enter your name and click "Confirm Outcome"

    The status updates, your name and the timestamp are recorded, and the file is auto-saved.

Completed and Failed records are terminal — no further status changes are possible. Only deletion is available.

6 Editing & Deleting

Editing a Record

Click the pencil icon (✎) in the Actions column to edit a Pending request. Editing is only available while a record is in Pending status — once checked, the record is locked.

When you save an edit, the Time Edited field is updated to the current timestamp. All other original fields (Time Added, original index) remain unchanged.

Deleting a Record

Click the red bin icon (🗑) to delete any record regardless of its status. A confirmation dialog will appear — this action cannot be undone. Deletion triggers an auto-save.

⚠
Deleting a Completed or Failed record will permanently remove it from the audit trail. Consider exporting records before deletion if historical data needs to be retained.

7 Search & Filter

The toolbar provides two ways to narrow down the records displayed in the table:

Search

Type anything into the search box to instantly filter records. The search checks the following fields simultaneously:

  • Record index number
  • User name
  • Project
  • Pool and Pool Account Number
  • Customer Name
  • Customer Sort Code and Bank Account
  • Amount
  • Date/time added
  • Checker and completer names
  • Status

The search is case-insensitive. Click the ✕ button inside the search box to clear the search and show all records.

Status Filter

Use the dropdown to show only records at a specific status. The search and status filter work together — for example, you can search for "J.Smith" and also filter to only show Pending records.

Sorting

Click any column header to sort by that column. Click again to reverse the sort order. The currently sorted column shows a small triangle indicator. Sorting is applied on top of any active search/filter.

8 Exporting Data

Click the Export button in the toolbar to open the Export dialog. You have three export scope options:

OptionWhat is exported
All recordsEvery request in the file, regardless of status.
Checked onlyOnly records with a status of Checked. This is the recommended option for bank submissions.
Current filtered viewOnly the records visible in the table right now (based on your active search/filter).

There is also an important checkbox at the bottom of the Export dialog:

✓
"Mark exported Checked records as Sent after export" — When ticked, any Checked records included in the export will automatically have their status updated to Sent once the CSV downloads. This is recommended for the standard bank-submission workflow as it keeps the data in sync with what has actually been submitted.

The exported file is a standard CSV that can be opened in Excel, Microsoft Dynamics, or any payment processing system. Sort codes and bank account numbers are exported using a special Excel text-force format (="12-34-56") to prevent Excel from misinterpreting them as dates or numbers.

9 Saving & Auto-Save

Manual Save

After adding or editing a record, a yellow dot appears on the Save button in the header bar. Click Save to write all changes to the CSV file on disk. A confirmation dialog will appear — click Save to confirm.

Your browser will only ask for file permission once per session. If you accidentally revoke permission, close and reopen the file.

Auto-Save

Certain actions trigger an automatic silent save without requiring you to click the Save button:

  • Marking a record as Checked
  • Marking a record as Sent (via the Export workflow)
  • Marking a record as Completed or Failed
  • Deleting a record

You will see a green "Saved ✓" toast notification in the bottom-right corner when an auto-save completes.

Background Sync (Multi-User)

While a file is open, the tool checks for external changes to the CSV file on disk every 15 seconds. If another user has saved changes in the meantime, those changes are merged silently into your view. You will see an orange toast notification informing you how many updates were synced. For more detail, see Section 11.

💡
Get into the habit of saving immediately after adding records — especially if others are working in the same file. This ensures your new entries have unique index numbers and reduces the chance of conflicts.

10 Statistics Dashboard

Click the Statistics tab to open the analytics dashboard. This provides a live summary of your data with powerful filtering tools.

Filter Bar

At the top of the Statistics tab is a filter bar with four controls:

  • Status — tick/untick checkboxes to include or exclude records by status in all charts and tables.
  • Project — filter to a single project using the dropdown.
  • Date Added (From / To) — restrict the data to a specific date range.
  • Reset button — clear all Statistics filters at once.

A summary pill on the right shows the current count and total value of records matching the active filters.

Breakdown Tables

The default inner tab shows four breakdown tables:

  • By Project — count and total value per project, with a visual bar indicator.
  • By User — how many requests each user has submitted and their combined value.
  • By Pool — activity and value per pool account.
  • By Status — aggregate count and value per status, with sent vs. unsent indicators.

Over Time Chart

Switch to the "Over Time" inner tab to see a bar chart showing the number of requests added per calendar month. Useful for identifying busy periods and trends.

Amounts Chart

The "Amounts" inner tab displays a histogram of transfer values, showing the distribution of request sizes. A summary below the chart shows total, average, minimum, and maximum amounts.

11 Multi-User Collaboration

The EFT Request Manager supports a basic form of concurrent multi-user access by sharing a single CSV file on a network drive. Here is how it works and what to be aware of.

How Collaboration Works

  • Each user opens the same CSV file in their own browser on their own computer.
  • Every 15 seconds, the tool silently checks whether the file on disk has been changed by someone else.
  • If changes are detected, they are merged into the current user's view using a timestamp-based strategy: the most recently modified version of each record wins.
  • New records added by other users appear automatically.
  • Records deleted by other users are removed automatically.
ℹ
Index collision prevention: when adding a new record, the tool reads the file from disk in real time to find the current highest index number, preventing two users from creating records with the same index even if they both click "Add Request" simultaneously.

Merge Behaviour

When two users have both made changes before either saves, the tool compares timestamps to decide which version to keep:

  • If the version on disk has a more recent activity timestamp (checked, completed, sent), the disk version's status fields are used.
  • If the version on disk has a more recent edit timestamp, the disk version's data fields are used.
  • Records that appear on disk but not in memory are added.
  • Records that exist in memory but were deleted from disk are removed (provided their "Time Added" predates the last known sync).

12 Caveats & Limitations

The EFT Request Manager is a practical, lightweight tool. It is important to understand its limitations before relying on it for critical financial operations.

⚠ No real-time locking

Two users can open and edit the same record simultaneously. The last person to save wins. There is no record-level locking or conflict warning. Coordinate with your team to avoid simultaneous edits to the same record.

⚠ 15-second sync delay

Background synchronisation runs every 15 seconds. Changes made by other users may not appear immediately. Critical updates should be communicated verbally or via messaging alongside the tool.

⚠ Chrome / Edge only

The File System Access API is not supported in Firefox, Safari, or Internet Explorer. All users must use Google Chrome or Microsoft Edge. The tool will not function at all in unsupported browsers.

⚠ Local / network file only

Data is stored in a CSV file on the user's local drive or a network share. It is not backed by a database server. If the file is deleted or the network share becomes unavailable, data may be lost. Regular backups are strongly recommended.

⚠ No user authentication

There is no login system. Anyone who can access the HTML file and the CSV file can add, edit, or delete records. The "User" and "Checker's Name" fields are free-text and are not verified against any user directory.

⚠ No bank integration

The tool does not connect to any bank or payment system. It produces a CSV export which must be manually uploaded to your payment platform. It does not verify sort codes or account numbers.

⚠ Large file performance

The tool holds all records in browser memory. Performance may degrade with very large files (thousands of records). Consider archiving completed records periodically by exporting and starting a new file for each year or quarter.

⚠ No undo functionality

There is no undo button. Deletions are permanent once the file is saved. Status changes (Checked, Sent, Completed, Failed) cannot be reversed through the interface — contact a system administrator if a rollback is needed.

⚠ Data in CSV is plain text

The CSV file contains sensitive financial data in plain text. Ensure the file is stored in a secure, access-controlled location. Do not store the file on a public or unprotected drive.

⚠ Session-only permissions

Browser file permissions are granted per session. Each time you open the HTML file in a new browser session, you will need to re-open the CSV and re-grant file access permission.

13 Tips & Best Practices

  1. Use a shared network drive — store the CSV on a shared drive accessible to all team members. This ensures everyone is working from the same data.
  2. Save frequently — always save after adding records. Do not rely solely on auto-save.
  3. Enforce the four-eyes rule — the Checker should always be a different person from the Requester. The tool does not enforce this, but your procedures should.
  4. Use consistent naming — standardise User names and Project codes across the team. This makes searching and the Statistics dashboard much more useful.
  5. Archive periodically — export completed records and start a new file each quarter or year to keep performance snappy and files manageable.
  6. Back up the CSV — schedule regular automated backups of the CSV file, especially before bulk exports or major operations.
  7. Double-check sort codes — the tool stores sort codes as text and does not validate them. Verify against your source documentation before checking any request.
  8. Communicate changes — if you are about to perform a bulk status change or delete records, let colleagues know so they are not mid-workflow at the same time.
  9. Keep the HTML file up to date — when a new version of the tool is released, replace the HTML file. The CSV data file is separate and unaffected by tool updates.
